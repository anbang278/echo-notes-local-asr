# M0 技术验证设计

## 输入与边界

产品边界以 docs/DESIGN.md、ARCHITECTURE.md 和 DEVELOPMENT_PLAN.md 为准；来源以 research/baseline.md 的固定提交为准。已存在的任务协议和 Swift 控制台是复用候选，不代表新项目已具备这些能力。首期采用 Python / MLX 推理进程与原生轻量控制界面的既定方向，M0 先用最小启动器验证运行包，不先开发完整 UI。

## 实验路线

Pi 在获授权后以新项目 main 建立持久 worktree 和 pi/m0-baseline-packaging 分支。先形成最小迁移清单及依赖分析，再选择明确来源、可再分发的独立解释器，锁定 Python / MLX / 解码器组合。每个选型需将来源、版本、依赖关系、分发条件与舍弃原因写入报告，不能靠复制开发 .venv 交付。

第一轮只迁入普通转写所需模块与必要测试；说话人／对齐模块只用于识别依赖边界，普通转写启动不得依赖其缓存。运行包与模型分开，显式指定测试数据、模型根和输出；缺模型直接失败。先证明本机文件输入到文本输出，再决定是否启服务测试协议。

## 数据、进程与错误

源码、运行包、模型、输入与日志分离。应用数据目录目标遵循 macOS 用户目录约定；具体路径及迁移策略在 M0 决策记录中固定。测试内容放新项目 test-data，安装放 test-install。测试实例先核验端口和旧服务锁，禁止绕开已有锁并发占用 MLX 或停止旧实例。

记录加载错误、依赖缺失、模型缺文件、解码失败、取消与进程重启实际表现。未经验证不承诺恢复语义，不把本机测试接口当新公开 API。

## 打包与分发判定

同时检查 arm64 原生扩展、动态库定位、解码组件、签名完整性和模型许可。没有 Developer ID 时可做开发运行实验，签名公证保持阻塞。跨路径验证通过后再去干净设备验证，开发机已有依赖不能被误算为随包组件。

Python 路线出现可复现阻塞时先形成失败记录；仅对阻塞点开展有界 Swift 推理对照，不直接重写全栈。改变既定架构或首期范围前回传 Codex 补齐决策。

## 输出

脱敏的基线迁移清单、组件清单、可执行复现命令、支持矩阵、测试报告、数据目录 ADR 与后续构建／测试交付入口。完整机器路径、诊断原文与录音保留本地忽略区，公开报告只给必要元数据。
